# P5.5 item 1: one core for voice and chat (merge `ChatCore` into `TurnCore`)

Owner (2026-10-24): first and required item of P5.5. Done when `turns/chat_core.py` and `src/turns/chatCore.js` are
gone, `VoiceSession` and `CallSession` / `Chat` are facades on one `TurnCore`, and the golden decisions are identical
(voice, and Chat as after P5). No behaviour change of any kind: same decisions, same `stats()` / counts, same events,
same outcomes, same calls to the agent and client, same timing on the voice path.

## Today

- `turns/turn_core.py` (voice): `decide()` = open turn, classify + rewrite (`VoiceTurn`), rule chains
  `before_filler` / `filler` / `question` (first objection), lookup in the budget, hit chain, serve. `record()` = pair
  (`TurnPairing`), `answer_given`, transcript, `before_sharing`, personal template or `sharing`, bounded write, question
  record. Host: `TurnHost` (`SessionHost`); call view: `VoiceCall` (`SessionCall`); readings: `CallReadings`.
- `turns/chat_core.py` (Chat): `handle()` = sharing mode, understand the frame (budget, replay fallback), note what the
  user told, `RuleChecker` (V1-V10: decisive / frame / question groups, every objection collected) -> verdict with
  route / key / segment / ttl, shared-question rules, urgent words, call state update, urgent and tools hooks, filler,
  lookup + hit chain (P5), the messages for a miss. `record()` = open-turn / cancelled pairing, note the reply, save
  check, bounded write, question record. Host: `ChatHost` (`CallSession`).

## The shape to reach (design it in detail before coding; write the design below this section)

- One `TurnCore` class with the fixed steps of a turn (Template Method): open the turn, understand, check the
  question, route (an early answer: filler, urgent, tools), look up within the budget, check the hit, serve or hand to
  the model; and on the answer: pair it with its turn, check it, write it (bounded), keep its question record.
- What differs between channels is **injected**, never a branch on the channel: an understanding step (voice: the
  classifier / rewriter slots; chat: the frame understander with its budget and replay fallback, and the user-told
  notes), a question check (voice: the rule chains; chat: `RuleChecker` plus the shared-question chain and urgent
  words), route handlers (filler; chat's urgent and tools hooks), the hit chain and its subject adapter, the pairing
  (voice `TurnPairing`; chat open / cancelled ids, unless they are provably the same), the save check, the writer and
  the records. Channel facts that are data (budgets, `spoken`, commitments) live on `Channel`; add `ChatChannel`
  data only where it is data.
- Small interfaces (`Protocol` / JSDoc typedefs), constructor injection; the facades (`VoiceSession`, `CallSession`,
  `Chat`) and the factories are the composition roots and the only places that pick the parts.
- The public results stay as they are: `TurnDecision` for voice, `TurnResult` and the outcome strings for Chat. If
  the core needs one internal result type, the facades adapt it (an Adapter, not a branch inside the core).
- Python first (one or more commits, each green), then Node mirroring it exactly (same class and file names, camelCase
  methods). CLAUDE.md section 4 rules apply.

## Design (settled 2026-10-24, after the "Splitting" rules; the Node port mirrors this)

### The one core: `turns/turn_core.py`, `TurnCore` (Template Method)

```
decide(said):
    turn = pairing.open()                            number the turn (and open it)
    early = answers.before_reading(said, turn)       chat: empty, registered filler, sharing off; voice: none
    checked = question_check.check_question(reader.read(said, turn))     stage 1 -> Checked(turn, objection)
    objection: answers.after_check(checked) or report.to_model(checked)   (filler; chat's urgent / tools hooks)
    looked = look_up(checked.subject)                lookup in the budget (CacheLookup) + hit_check.check_hit
    objection: report.missed(checked, looked)   else report.served(checked, looked)
record(answered):
    report.recorded(answered, outcome)               voice: count the save rule; chat: the "answer" event
    outcome = pairing.settle -> saving.check (stage 3) -> saving.write, inside the one write boundary
              (report.kept(verdict) for a dropped or kept answer, report.refused(error) for a failed write)
```

The turn's number flows as a value (`pairing.open()` returns it; the reading carries it: `VoiceTurn.number`,
`ChatReading.turn_id`), never as shared state, so two voice `decide()` calls on two threads keep their own
numbers as before. The facades only call the core: `VoiceSession.decide()` = `core.decide()`,
`_record_model_turn()` = `core.record(VoiceAnswered(...))`; `CallSession.handle()` = `core.decide()`,
`record_answer()` = `core.record(ChatAnswered(...))`. (`VoiceSession.record()` / `answer()` still check the
decision and fill it from the outcome: that is the public API's own contract.)

### The parts (`turns/turn_steps.py`): each interface has a voice and a chat implementation

| Part | Voice | Chat | Why two |
|---|---|---|---|
| `Pairing` (`open() -> int`, `settle`) | `VoicePairing` over `runtime.TurnPairing`: every decided turn numbered and opened at the transcript's end; a moved-on answer is `Interrupted` | `ChatTurns`: numbering; only a turn the agent must answer awaits one (a filler, urgent script or tools answer leaves the previous turn open); `Cancelled` / `Stale` | different pairing semantics |
| `EarlyAnswers` | `VoiceReport`: none before reading; a filler rule's answer after the check | `ChatAnswers`: empty, filler, sharing off; `on_urgent` / `urgent_reply` / `on_tools` | voice checks fillers as a rule after reading; chat screens before it understands |
| `TurnReader` | `VoiceReader`: classifier, rewriter, `RewriteCheck` -> `VoiceTurn` | `ChatReader`: frame in its budget, replay fallback, user-told notes -> `ChatReading` | different understanding |
| `QuestionCheck` | `RuleSet` itself (first objection) | `ChatQuestionCheck`: `RuleChecker` (every objection), shared-question chain, urgent words, state update | different rule sets and reporting |
| `HitCheck` | `RuleSet.check_hit` (confidence is a rule) | `ChatHitCheck`: an unconfident hit stops uncounted before the rules; a refusal counts the rule's name; `ChatHitCall` / `ChatHitTurn` adapt the hit side | different counting |
| `Report` | `VoiceReport`: `TurnDecision` / `_Outcome`, `Stats`, transcript, audio; stamps every decision with its turn and session, builds `messages` / `cacheable` (`model_messages`) and offers the sharing to `TurnPairing` | `ChatReport`: `TurnResult` / outcome strings, `counts`, "turn" / "answer" events, the miss's messages | different public results |
| `Saving` | `VoiceSaving`: `ModelAnswer`, voice save chains, transcript, personal templates (`share_templates`), bounded `learn` in the call's segment, question record, `last_stored` | `ChatSaving`: reply note, not shared, `save_check`, bounded write, question record | different save rules and subjects |
| `CallSettings` | the `VoiceSession` itself | the `CallSession` itself | read live |

Parts read the session through small per-part `Protocol`s of its public, live attributes (as Chat's parts
always did); no host adapter.

### Merged or collapsed in this pass

- `ChatCachedAnswer` -> `CachedAnswer` (a chat hit's turn is a `ChatHitTurn`, never personal, so `answer` is
  the hit's); `chat_cached_answer.py` gone, its two adapters live in `chat_hit_check.py`.
- The bounded write's "twice the budget, or wait without one" is one method, `BoundedWriter.write_within`, used
  by both savings.
- `SessionHost` and `TurnHost` gone (forward-only): the session is the core's `CallSettings`; `VoiceReport`
  gets the transcript and `voiced`; `VoiceSaving` owns the writes (`_learn`, `_learn_personal`, the question
  record, `last_stored`).
- `SessionCall` is no longer forward-only: it owns the call's context (`chain`, `context_key`, `after_urgent`,
  `said_identifiers`, `engine_vouches`, `answers_another_question`, `agent_key`, `question_records`), moved out
  of `VoiceSession`; `VoiceCall` stays the rules' interface (second implementation: the tests' `FakeCall`).
- Out of the facades: `VoiceSession._decide`, `_model_messages` (now `VoiceReport.model_messages`), `_moved_on`,
  `_count`, the seven call-context methods; the rule count after a record (`VoiceReport.recorded`); the
  "answer" event (`ChatReport.recorded`); `CallSession._emit`, `_prompt_key`, `_norm`.
- `turns/`: 33 files -> 30; forward-only classes 2 -> 0.
