  `before_filler` / `filler` / `question` (first objection), lookup in the budget, hit chain, serve. `record()` = pair

## The shape to reach (design it in detail before coding; write the design below this section)

- One `TurnCore` class with the fixed steps of a turn (Template Method): open the turn, understand, check the
  question, route (an early answer: filler, urgent, tools), look up within the budget, check the hit, serve or hand to
  the model; and on the answer: pair it with its turn, check it, write it (bounded), keep its question record.
- What differs between channels is **injected**, never a branch on the channel: an understanding step (voice: the
  classifier / rewriter slots; chat: the frame understander with its budget and replay fallback, and the user-told
  notes), a question check (voice: the rule chains; chat: `RuleChecker` plus the shared-question chain and urgent
  words), route handlers (filler; chat's urgent and tools hooks), the hit chain and its subject adapter, the pairing
  (voice `TurnPairing`; chat open / cancelled ids, unless they are provably the same), the save check, the writer and
  the records. Channel facts that are data (budgets, `spoken`, commitments) live on `Channel`; add `ChatChannel`
  data only where it is data.
- Small interfaces (`Protocol` / JSDoc typedefs), constructor injection; the facades (`VoiceSession`, `CallSession`,
  `Chat`) and the factories are the composition roots and the only places that pick the parts.
- The public results stay as they are: `TurnDecision` for voice, `TurnResult` and the outcome strings for Chat. If
  the core needs one internal result type, the facades adapt it (an Adapter, not a branch inside the core).
- Python first (one or more commits, each green), then Node mirroring it exactly (same class and file names, camelCase
  methods). CLAUDE.md section 4 rules apply.

## Design (written by the implementer before coding)

### The one core: `turns/turn_core.py`, `TurnCore` (Template Method)

```
decide(said):
    pairing.open()                                   open the turn
    early = answers.before_reading(said)             operational answers before reading (chat: empty, filler, off)
    turn = reader.read(said)                         understand
    checked = question_check.check_question(turn)    stage 1 -> Checked(turn, objection)
    objection: answers.after_check(checked) or report.to_model(checked)   (filler; chat's urgent / tools hooks)
    looked = look_up(checked.subject)                lookup in the budget (CacheLookup) + hit_check.check_hit (stage 2)
    objection: report.missed(checked, looked)   else report.served(checked, looked)
record(answered):
    paired = pairing.settle(answered)                -> Checked(answered, dropped verdict)
    checked = saving.check(paired.subject)           stage 3 -> Checked(answer, objection)   objection: report.kept(v)
    try: saving.write(answer)  except: report.refused(error)        the one write boundary
look_up(turn) -> LookedUp(hit, cached, objection):
    settings.agent.ask(turn.key, serve_above, cheap_above=min(0.60, serve_above), **turn.lookup_options)
    inside the lambda, so the pool thread evaluates the key and options as today (voice timing unchanged)
```

The core never names a channel; it reads `settings` (`CallSettings`: `agent`, `serve_above`,
`latency_budget_ms`, read live) and calls the injected parts. A dropped answer, a save objection and a
question objection are all a `Verdict`; the channel's `Report` turns them into its public result.

### The injected parts (`turns/turn_steps.py`: small `Protocol`s, one method or two each)

| Part | Interface | Voice | Chat |
|---|---|---|---|
| `Pairing` | `open()`, `settle(answered) -> Checked` | `VoicePairing`: `TurnPairing` opened at the transcript's end; a moved-on answer is `Interrupted` | `ChatTurns`: numbering, the open turn, cancelled ids; `Cancelled` (counted) / `Stale`; `cancel()`, `next_turn` |
| `EarlyAnswers` | `before_reading(said)`, `after_check(checked)` | `VoiceReport`: nothing before reading; after the check a rule that answered (`verdict.answer`: the filler) | `ChatAnswers`: empty, registered filler, sharing off; then the `on_urgent` / `urgent_reply` / `on_tools` hooks |
| `TurnReader` | `read(said) -> turn` | `VoiceReader`: classifier, rewriter, `RewriteCheck`, `CallReadings` -> `VoiceTurn` | `ChatReader`: the frame within its budget, replay fallback, the user-told notes, names, language -> `ChatReading` |
| `QuestionCheck` | `check_question(turn) -> Checked` | `RuleSet`: `before_filler`, `filler`, `question` (first objection) | `ChatQuestionCheck`: `RuleChecker`, shared-question chain, urgent words, state update, route count; keys the reading |
| `HitCheck` | `check_hit(turn, hit, started) -> Checked` | `RuleSet`: `CachedAnswer` + `hit` chain | `ChatHitCheck`: not confident (uncounted), `ChatCachedAnswer` + hit chain, counted by rule name |
| `Report` | `to_model`, `missed`, `served`, `kept`, `refused` | `VoiceReport`: `TurnDecision` / `_Outcome`, `Stats`, transcript, audio | `ChatReport`: `TurnResult` / outcome strings, `counts`, events, notes of the agent's reply, opens the turn |
| `Saving` | `check(answered) -> Checked`, `write(answer)` | `VoiceSaving`: `ModelAnswer`, `answer_given`, key, transcript, `before_sharing`; write: personal shape or `sharing` chain + bounded `learn` + question record | `ChatSaving`: the reply note, not shared, save rules (`save_check`); write: bounded write, `saved`, question record |

Value objects: `Checked(subject, objection)` and `LookedUp(hit, cached, objection)` (`turns/checked.py`);
`VoiceAnswered` / `ChatAnswered` (`turns/answered.py`): what each facade hands `record()`;
`ChatReading` (`turns/chat_reading.py`): a chat turn as read, then keyed by its check (`checked_as`),
with `key` / `lookup_options` like `VoiceTurn`.

Channel data stays data: the lookup's counters are `CacheLookup` arguments (chat: `lookup_timeouts` /
`lookup_errors`; voice keeps its defaults), `refuse_late_hits` as today, budgets on the session.

### Kept identical

- **Pairing**: not unified, because it is provably different: voice numbers every decided turn (a
  filler moves the call on); chat's open turn is only one the agent must answer (a filler, an urgent
  script or a tools answer leaves the previous turn open). Both sit behind `Pairing`.
- **Counts / stats**: voice counts through `Stats` (verdict counters + `count_rule`), chat through its
  `counts` dict; every verdict carries the counters it adds (chat's lookup verdicts get chat names from
  `CacheLookup`, its hit objections count the rule name, as today).
- **Events**: built and emitted only by `ChatReport` / `ChatAnswers` (same dicts, same order);
  `record_answer` still emits the answer event in `CallSession`.
- **Public results**: `TurnDecision` and `_Outcome` (voice), `TurnResult` and the outcome strings
  (`saved`, `slow_write`, `not_shared`, `refused:<why>`, `cancelled`, `stale`) are built only by the
  channel's `Report` (Adapter); the facades' signatures do not change.
- **Order and timing**: every step runs in today's order (voice still reads the turn before its
  fillers; chat screens before it understands); the lookup lambda evaluates what it did; the write
  boundary covers what it covered (voice: the personal / sharing rules and the writes; chat: the write).

### Why this is not over-engineered

- Each part holds code that existed (moved, not rewritten) and differs between the channels; nothing
  is added for a third channel. Where a part is just rules (voice's question and hit checks) the
  `RuleSet` is the part: no wrapper class. Voice's filler is a result, so `VoiceReport` answers it.
- No part only forwards: `VoicePairing` translates turn numbers into a verdict and the shareable flag;
  every chat part owns the logic `ChatCore` had for that step.
- One generic step result (`Checked`) instead of a result type per step; one core instead of two.
- Not unified on purpose (behaviour would change): voice reading before its fillers, the two pairings,
  the per-channel counters, chat's uncounted not-confident hit.
